## Descripción

El firmware actual envía valores de aceleración convertidos a m/s² (floats). Esto limita la magnitud a rangos de 50-100 para golpes fuertes. Esta feature define el protocolo V2 del firmware que envía valores raw int16 del ADC divididos por 16, obteniendo números enteros en rango ~100-1500+ que se corresponden mejor con la percepción real de potencia del usuario (similar a sistemas comerciales como Brooklyn Fitboxing).

También actualiza el tipo `SensorReading` y la lógica de la app para recibir y procesar estos nuevos valores. El campo `magnitude` en `Impact` pasa a almacenar el valor raw escalado (entero positivo), mientras que `intensity` (0-100) sigue siendo la escala interna para detección y validación de golpes.

## Criterios de aceptación

- [ ] Existe `docs/SENSOR-TECNICO-V2.md` con el nuevo protocolo BLE (raw int16 / 16)
- [ ] El firmware V2 envía `ax, ay, az` como `int16` divididos por 16 (enteros) en lugar de floats en m/s²
- [ ] El packet BLE V2 tiene formato: `uint32 timestamp + int16 ax + int16 ay + int16 az + int16 gx + int16 gy + int16 gz` = 16 bytes
- [ ] `SensorReading.magnitude` se calcula en la app como `Math.round(Math.sqrt(ax²+ay²+az²))` con los valores raw/16
- [ ] El umbral de detección (`profile.threshold`) y la escala (`profile.sensitivity`) siguen siendo configurables y funcionan correctamente con la nueva escala de magnitud
- [ ] Los perfiles existentes muestran un aviso de que los valores de calibración deben ajustarse al cambiar al firmware V2
- [ ] `Impact.magnitude` almacena el valor raw escalado (entero, positivo)
- [ ] La app desktop y mobile parsean correctamente el nuevo packet de 16 bytes

### Protocolo BLE V2

**Packet anterior (V1) — 28 bytes:**
```
bytes 0-3:   uint32  timestamp (ms)
bytes 4-7:   float32 ax (m/s²)
bytes 8-11:  float32 ay (m/s²)
bytes 12-15: float32 az (m/s²)
bytes 16-19: float32 gx (°/s)
bytes 20-23: float32 gy (°/s)
bytes 24-27: float32 gz (°/s)
```

**Packet nuevo (V2) — 16 bytes:**
```
bytes 0-3:   uint32  timestamp (ms)
bytes 4-5:   int16   ax  (raw ADC / 16)
bytes 6-7:   int16   ay  (raw ADC / 16)
bytes 8-9:   int16   az  (raw ADC / 16)
bytes 10-11: int16   gx  (raw ADC / 16)
bytes 12-13: int16   gy  (raw ADC / 16)
bytes 14-15: int16   gz  (raw ADC / 16)
```

La versión del sensor se lee de `VERSION_CHARACTERISTIC_UUID` al conectar (ya implementado). V2 → parse nuevo packet.

### Firmware V2 (cambios respecto a V1)

```cpp
// Reemplaza getEvent() por getAcceleration() / getRotation() raw
int16_t ax_raw, ay_raw, az_raw, gx_raw, gy_raw, gz_raw;
mpu.getAcceleration(&ax_raw, &ay_raw, &az_raw);
mpu.getRotation(&gx_raw, &gy_raw, &gz_raw);

// Escalar dividiendo por 16
int16_t ax = ax_raw / 16;
int16_t ay = ay_raw / 16;
int16_t az = az_raw / 16;
int16_t gx = gx_raw / 16;
int16_t gy = gy_raw / 16;
int16_t gz = gz_raw / 16;

// Packet de 16 bytes
uint8_t buffer[16];
memcpy(&buffer[0], &timestamp, 4);
memcpy(&buffer[4],  &ax, 2);
memcpy(&buffer[6],  &ay, 2);
memcpy(&buffer[8],  &az, 2);
memcpy(&buffer[10], &gx, 2);
memcpy(&buffer[12], &gy, 2);
memcpy(&buffer[14], &gz, 2);

// Magnitud para shouldNotify (en unidades raw/16)
int32_t mag2 = (int32_t)ax*ax + (int32_t)ay*ay + (int32_t)az*az;
float magnitude = sqrt((float)mag2);
```

**`SENSOR_VERSION` pasa a 2** en el define del firmware.

### Cálculo de magnitud en la app

```ts
// Con V2, ax/ay/az son enteros (raw/16)
// magnitude sigue siendo Math.sqrt(ax²+ay²+az²), pero ahora el resultado es entero grande
reading.magnitude = Math.round(Math.sqrt(ax*ax + ay*ay + az*az))

// Rangos esperados con ±16g y factor /16:
// Reposo (1g ≈ 2048 raw → 128 raw/16): magnitude ≈ 128
// Golpe normal (5g ≈ 10240 raw → 640 raw/16): magnitude ≈ 640
// Golpe fuerte (10g+ ≈ 20480 raw → 1280 raw/16): magnitude ≈ 1280+
```

### Compatibilidad V1/V2

La app ya lee `SENSOR_VERSION` al conectar. Añadir lógica de parse condicional:

```ts
if (sensorVersion === 2) {
  // parse 16 bytes con int16
} else {
  // parse 28 bytes con float32 (V1 actual)
}
```

No se añaden campos nuevos. Se actualiza el comentario en `SensorReading`:

```ts
export interface SensorReading {

  ay: number
  az: number
  gx: number
  gy: number
  gz: number

```

## Escenarios de test

1. **Parse correcto de packet V2**
   - **Given**: buffer de 16 bytes con timestamp=1000, ax=640, ay=0, az=128, gx=0, gy=0, gz=0
   - **When**: se parsea como V2
   - **Then**: `reading.ax = 640`, `reading.magnitude = Math.round(sqrt(640²+128²)) = 652`

2. **Magnitud en reposo con V2**
   - **Given**: sensor en reposo, az ≈ 2048/16 = 128 (gravedad), ax≈ay≈0
   - **When**: se calcula magnitude
   - **Then**: magnitude ≈ 128 (entero positivo)

3. **Golpe fuerte genera número >1000**
   - **Given**: ax=800, ay=600, az=128 (golpe fuerte)
   - **When**: magnitude = Math.round(sqrt(800²+600²+128²))
   - **Then**: magnitude = Math.round(sqrt(1016384)) ≈ 1008 (>1000)

4. **Backward compat: V1 sigue funcionando**
   - **Given**: sensor con SENSOR_VERSION=1 conectado
   - **When**: se parsea el packet
   - **Then**: se usa el parser de 28 bytes (floats), sin errores

## Notas de implementación

- El documento `SENSOR-TECNICO-V2.md` debe incluir el código completo del firmware para poder flashear desde Arduino IDE.
- Los valores de `threshold` en los perfiles existentes estaban calibrados para m/s² (ej. 15.0). Con V2 los valores de magnitud son ~10× mayores — el usuario deberá recalibrar. El agente dev no necesita migrar perfiles existentes, solo documentar el cambio de escala.
- El giroscopio (gx/gy/gz) se incluye en el packet por coherencia pero actualmente no se usa en la lógica de detección.
