## Descripción

Sincroniza los perfiles de calibración (`profiles.json`) con Google Drive, permitiendo compartirlos entre dispositivos. A diferencia de las sesiones (que se acumulan por ID único), los perfiles pueden crear conflictos reales si se modifican en dos dispositivos distintos. Cuando se detecta conflicto se muestra un diálogo para que el usuario decida.

## Criterios de aceptación

- [ ] Al guardar o modificar un perfil, se sube `profiles.json` a Drive automáticamente (si cuenta conectada)
- [ ] Al conectar cuenta Google, se descarga `profiles.json` de Drive y se compara con el local
- [ ] Si no existe `profiles.json` en Drive: se sube el local (primera vez)
- [ ] Si no existe local pero sí en Drive: se descarga directamente sin diálogo
- [ ] Si existen ambos y son idénticos (mismo contenido): no se hace nada
- [ ] Si existen ambos y son distintos: se muestra diálogo de resolución de conflicto
- [ ] El diálogo de conflicto ofrece: "Usar Drive", "Usar Local", "Combinar (mantener todos los perfiles únicos)"
- [ ] "Combinar" hace merge por `profile.id`: une perfiles de ambas versiones; si mismo ID existe en ambos, gana la versión de Drive (más reciente por diseño)
- [ ] Tras resolver el conflicto, la versión resultante se guarda en local y se sube a Drive
- [ ] Al crear, editar o eliminar un perfil, la subida a Drive es automática y silenciosa

### Lógica de negocio

#### Subida automática de perfiles
Tras cualquier mutación en `profileStore` (`addProfile`, `updateProfile`, `deleteProfile`):
```ts
if (driveStore.account) {
  await driveSync.uploadProfiles(profileStore.profiles)
}
```

`uploadProfiles()` serializa el array completo y hace upsert del archivo `profiles.json` en `appDataFolder`:
- Si el archivo no existe en Drive → crear
- Si ya existe → actualizar (PUT con el nuevo contenido)

#### Detección de conflicto al conectar cuenta
```ts
async function syncProfilesOnConnect(localProfiles: CalibrationProfile[]) {
  const remoteJson = await driveApi.downloadFile('profiles.json')  // puede no existir

  if (!remoteJson) {
    // Drive vacío: subir local
    await uploadProfiles(localProfiles)
    return
  }

  if (!localProfiles.length) {
    // Local vacío: bajar Drive
    profileStore.setProfiles(JSON.parse(remoteJson))
    return
  }

  const remoteProfiles: CalibrationProfile[] = JSON.parse(remoteJson)
  
  if (JSON.stringify(localProfiles) === JSON.stringify(remoteProfiles)) {
    // Idénticos: no hacer nada
    return
  }

  // Conflicto: mostrar diálogo
  driveStore.setProfileConflict({ local: localProfiles, remote: remoteProfiles })
}
```

#### Resolución de conflicto: Combinar (merge)
```ts
function mergeProfiles(local: CalibrationProfile[], remote: CalibrationProfile[]): CalibrationProfile[] {
  const merged = new Map<string, CalibrationProfile>()
  
  // Añadir todos los locales
  for (const p of local) merged.set(p.id, p)
  
  // Remote sobrescribe en caso de conflicto de ID
  for (const p of remote) merged.set(p.id, p)
  
  return Array.from(merged.values()).sort((a, b) => a.createdAt - b.createdAt)
}
```

#### Modal de conflicto (UI)
Mostrado como modal sobre la pantalla de Perfiles. Contenido:

```
⚠️ Conflicto de perfiles

Este dispositivo tiene X perfiles.
Tu cuenta Drive tiene Y perfiles.

¿Qué quieres hacer?

[ Usar Drive ]     → Reemplaza local con Drive
[ Usar Local ]     → Sube local a Drive, descarta Drive
[ Combinar ]       → Une todos los perfiles únicos (recomendado)
```

El modal no se puede cerrar sin elegir una opción (es una decisión requerida para continuar la sync).

#### Cuándo se puede producir conflicto real
El conflicto solo ocurre si:
1. El usuario usó la app en el dispositivo A sin conexión y modificó perfiles
2. Luego abrió la app en el dispositivo B (con Drive) que tenía perfiles diferentes
3. Al reconectar A a internet

En uso normal (un dispositivo con internet), nunca hay conflicto.

## Escenarios de test

1. **Escenario**: Primera conexión con perfiles locales existentes
   - **Given**: Local tiene 2 perfiles; Drive no tiene `profiles.json`
   - **When**: `syncProfilesOnConnect(localProfiles)` es llamado
   - **Then**: `driveApi.uploadFile` es llamado con los 2 perfiles serializados; no se muestra diálogo

2. **Escenario**: Dispositivo nuevo con Drive ya poblado
   - **Given**: Local tiene 0 perfiles; Drive tiene `profiles.json` con 3 perfiles
   - **When**: `syncProfilesOnConnect([])`
   - **Then**: `profileStore.setProfiles` es llamado con los 3 perfiles de Drive; no se muestra diálogo

3. **Escenario**: Merge combina perfiles únicos y Drive gana en conflicto de ID
   - **Given**: Local = `[{id:'a', name:'Ligero'}, {id:'b', name:'Medio'}]`; Remote = `[{id:'a', name:'Ligero v2'}, {id:'c', name:'Potencia'}]`
   - **When**: `mergeProfiles(local, remote)`
   - **Then**: Resultado tiene 3 perfiles: `{id:'a', name:'Ligero v2'}` (Drive gana), `{id:'b'}`, `{id:'c'}`

4. **Escenario**: Perfiles idénticos no disparan conflicto
   - **Given**: Local y remote tienen exactamente el mismo JSON
   - **When**: `syncProfilesOnConnect(localProfiles)`
   - **Then**: No se muestra modal, no se hace ninguna llamada a Drive

5. **Escenario**: Modificar un perfil dispara subida automática
   - **Given**: Cuenta conectada; `driveApi.uploadFile` mockeado
   - **When**: `profileStore.updateProfile({...perfil, name: 'Nuevo nombre'})`
   - **Then**: `driveApi.uploadFile` es llamado con el array completo de perfiles actualizado

## Notas de implementación

- **`profiles.json` como array plano**: no hay versioning complejo. El archivo en Drive es simplemente `JSON.stringify(profiles)`. No fragmentar en archivos individuales por perfil (a diferencia de las sesiones).
- **Orden del modal**: el diálogo de conflicto se muestra en la pantalla de Perfiles, no en un splash o carga inicial. El usuario puede seguir usando la app mientras el modal está pendiente, pero las operaciones de Drive quedarán en pausa hasta que resuelva.
- **Sincronización de `deviceStore`**: fuera del scope de esta feature. Los dispositivos BLE son locales a cada hardware, no tiene sentido sincronizarlos entre móvil y desktop.
